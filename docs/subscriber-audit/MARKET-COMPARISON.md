# Subscriber platform comparison

This is a functional comparison for Issue #95 and parent #38, using MikroDash baseline `ba39515f003484211afe3dfef783ade6dc39f813`. All external citations were accessed **2026-11-13**; each has **confidence: Medium, tier: Primary** unless explicitly qualified. Vendor documentation establishes described functionality, not independently measured reliability, throughput or MikroDash compatibility. Implementation proposals below are analysis. No competitor code or protected interface design was copied.

## Documented platforms and version boundaries

**Splynx** documents customer activity, configurable policy testing, financial workflows and self-service. Its official v6.0 notes were available, but the exact latest patch/build and that page's publication timestamp were not established. The public changelog rendering still started with v5.2 dated 2026-01-22, so it cannot establish the latest release. A material documentation difference concerns live bandwidth: the older wiki requires PPP, while v6.0 adds native MikroTik DHCP/IPoE simple-queue statistics. Weight the explicit versioned change for v6.0 and retain the older restriction for earlier behavior. [Splynx v6.0](https://splynx.com/product-updates/release-notes-splynx-v-6-0/), [older bandwidth guide](https://wiki.splynx.com/network-management/routers_settings/mikrotik_live_bandwidth), [public changelog](https://splynx.featurebase.app/changelog).

**DMA Radius Manager** has verified public revision evidence for **4.10.5, 2025-10-28**. Its manual covers separate PPP/HotSpot setup, service assignment, card issuance and reseller accounting. Revision notes include RouterOS 7+ fixes, illustrating why support must be version-qualified. These sources do not certify MikroDash's target routers. [DMA revisions](https://www.dmasoftlab.com/revision), [DMA manual, 2025-09-01](https://www.dmasoftlab.com/documents/user_manual.pdf).

**Powerlynx** has a verified SaaS changelog entry dated **2026-11-11**, without a verified numeric build. Its documentation describes location-aware HotSpot, voucher inventory and reseller/payment workflows. Plan day/hour availability restricts purchase time; it must not be mistaken for an authenticated session's permitted access hours. [Powerlynx changelog](https://feedback.powerlynx.app/changelog), [data plans](https://docs.powerlynx.app/system/data-plans.html).

**MikroTik User Manager** provides the protocol-adjacent reference for profiles, limitations, sessions and migration. The current manual identifies documentation version **7.26**; that is not a verified stable firmware release or installed device version. Package/license availability remains device-dependent. **UISP CRM** provides an additional customer/service, billing and provisioning reference; its latest stable product version was not verified, and native MikroTik RADIUS support is not established by the selected documentation. [User Manager](https://manual.mikrotik.com/docs/authentication-authorization-accounting/user-manager/), [UISP client/service model](https://help.uisp.com/hc/en-us/articles/22590965763991-UISP-Site-Device-Management).

## Key findings and implementation decisions

The strongest recurring operational pattern is traceability across customer, service and network state. Splynx exposes account activity; UISP associates commercial services with client sites. For MikroDash, this suggests building on existing account/subscription identity and audit tables, then adding scoped detail reads. A second customer database or parallel usage authority would weaken that relationship. [Splynx customer information](https://wiki.splynx.com/en/customer_management/customer_information), [UISP services](https://help.uisp.com/hc/en-us/articles/22590965763991-UISP-Site-Device-Management).

Policy expressiveness needs an explanation path. The FUP benchmark includes preview/testing; MikroDash already has an evaluator, periods and immutable plan references. The priority is complete editors and acceptance around those components, followed by measured enforcement, rather than replacing the policy engine. [Splynx FUP](https://wiki.splynx.com/network-management/bandwidth_management/fup).

Voucher inventory and financial finality are distinct. Powerlynx describes stock and sale state separately from sessions, while payment attempts can remain unconfirmed. Its documentation does not prove transactionally atomic batch issuance or recoverable secret delivery. Those are MikroDash acceptance requirements derived from this task, not competitor guarantees. [Powerlynx reseller portal](https://docs.powerlynx.app/system/reseller-portal.html), [payments](https://docs.powerlynx.app/system/payments.html).

Successful protocol responses cannot establish every applied outcome. UISP documents propagation delay, and PPP AAA has its own settings and address precedence. MikroDash should retain desired/applied state separation and test PPPoE independently of HotSpot. [UISP shaping](https://help.uisp.com/hc/en-us/articles/22590998317719-UISP-Suspension-Traffic-Shaping-and-Aggregation), [PPP AAA](https://manual.mikrotik.com/docs/authentication-authorization-accounting/ppp-aaa/).

Migration must preserve interpretation as well as rows. User Manager conversion includes counters and sessions; that does not determine what should count against a new commercial period. MikroDash needs reviewed opening balances and explicit mapping before an importer can safely apply data. [User Manager](https://manual.mikrotik.com/docs/authentication-authorization-accounting/user-manager/).

## Priorities, uncertainties and next steps

First integrate reviewed P0 input, plan and history work without duplicating #77-#81. Then implement credential reset and idempotent entitlement operations; use those contracts for recoverable voucher batches, paged administration, live sessions and resumable migration. Add financial/reseller/notification modules after ownership and operation boundaries are testable. This order is analysis grounded in the local dependency gaps; acceptance and affected files are in [DEVELOPMENT-ROADMAP.md](DEVELOPMENT-ROADMAP.md).

The RouterOS RADIUS manual contains conflicting direction descriptions: its attribute text maps Input-Octets to traffic received from the client and Output-Octets to traffic sent to it, but another warning assigns output to client upload. Keep this unresolved until asymmetric physical-target captures qualify the protocol/device/firmware. Do not reverse production counters from documentation alone. Rate-limit Rx/Tx semantics are a separate question. [RouterOS RADIUS](https://manual.mikrotik.com/docs/authentication-authorization-accounting/radius/).

No selected sources establish competitor exactly-once notification delivery, Powerlynx batch rollback guarantees or native PPPoE support. No live competitor tenant, payment gateway, router or benchmark was exercised. Next evidence must include fault-injected operation rollback, response-loss recovery, independent protocol integration and bounded 100/1,000/10,000/100,000 synthetic datasets where resources allow. Synthetic success remains separate from Issue #76 physical acceptance; no release, deployment or authentication cutover follows from this comparison.
